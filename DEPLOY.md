# Deploying this site with GitHub Pages

The `production/` directory is a static export — plain HTML, CSS and JavaScript.
GitHub Pages can host it for free. `.github/workflows/deploy.yml` publishes
`production/` on every push to `main` that touches it, and can also be run
manually from the Actions tab.

## The URL has to be a domain root

This is the one real constraint, and it is worth understanding before you pick a
repository name.

The export links to its own pages with root-relative URLs (`/assets/site.css`,
`/privacy/`, `/demo/#system-demo`), and the client-side router reads the route
straight off `window.location.pathname`, anchored at `/`. Served from a
sub-path, the stylesheet and script 404 and every route resolves to the 404
page.

So there are two supported shapes:

| Shape | Repository name | Live URL |
|---|---|---|
| User / organisation site | `<your-github-username>.github.io` | `https://<your-github-username>.github.io/` |
| Any repo + custom domain | anything | `https://yourdomain.com/` |

A normal project site — `https://<user>.github.io/<repo>/` — will **not** work
with this build. The deploy workflow fails with an explanatory error rather than
publishing a broken site.

Rewriting the built output to tolerate a sub-path is not worth doing: the URLs
are regenerated by React after hydration, so patching the shipped HTML is not
enough. If you ever need a project-site URL, add base-path support in
`agency-source/components/service-capture/site.tsx` (the link builder and the
`window.location.pathname` route lookup) and rebuild with `npm run build:preview`.

## First-time setup

1. Create the repository on GitHub, named per the table above.
2. Push this repository to it (`git remote add origin …` then `git push -u origin main`).
3. In the repository, open **Settings → Pages** and set **Source** to
   **GitHub Actions**.
4. Open the **Actions** tab. The deploy runs automatically; the finished run
   prints the live URL.

The repository must be public, or on a plan that includes Pages for private
repositories.

### Adding a custom domain

1. Put the bare domain in a file at `production/CNAME`, one line, no protocol:
   `yourdomain.com`
2. At your DNS provider, point the domain at GitHub Pages (`A` records to
   GitHub's Pages IPs for an apex domain, or a `CNAME` to
   `<user>.github.io` for a subdomain).
3. Set the domain under **Settings → Pages**, and enable **Enforce HTTPS** once
   the certificate is issued.

## What is still unconfigured

Publishing makes the site reachable; it does not make it finished. Everything
below lives in `agency-source/config/site.ts` and is empty in this build, so the
export reflects that:

- **The contact form cannot receive enquiries.** `contactFormEndpoint` is empty,
  so a submission is refused up front with "This form is not connected yet. Your
  request has not been sent." Nothing is silently dropped and the visitor is told
  plainly — but no one can actually reach you through the site until you connect
  an endpoint. This is the item to fix before you point anyone at it.
- **No business email, phone or mailing address.** Those links are hidden while
  the values are empty.
- **No domain set.** `websiteDomain` feeds the page metadata base.
- **No calendar URL.** Every "book a review" call to action falls back to the
  contact form.
- **Analytics is inactive**, by design.

Privacy, Terms and Accessibility are drafts and say so. EverWarm is a fictional
company used for the demo, not a client or a case study.

Change values in `agency-source/config/site.ts`, rebuild with
`npm run build:preview`, and copy the generated `out/production/` over
`production/` before committing. See `README.md` for the full build and launch
checklist.

## Connecting the contact form

The form posts JSON and only reports success when the service confirms receipt
in its own response shape. A plain endpoint you control should return
`{"accepted": true}`; nothing else in `config/site.ts` is then needed.

Hosted form services do not return that shape, so `contactFormProvider` selects
a small adapter:

```ts
contactFormEndpoint: "https://api.web3forms.com/submit",
contactFormProvider: "web3forms",
contactFormAccessKey: "<your access key>",
```

The Web3Forms access key is public by design — it names the destination inbox
and ships in the browser bundle. It is not a secret, and no private API key of
any kind belongs in this file.

Selecting a provider without its key leaves the form honestly unconnected rather
than half-wired: it refuses submission with the same "not connected yet"
message.

Rebuild and copy `out/production/` over `production/` for the change to reach
the live site.
